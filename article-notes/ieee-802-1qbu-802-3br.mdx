## Two standards, two layers

| | [IEEE 802.3br](https://www.ieee802.org/3/br/) | [IEEE 802.1Qbu](https://standards.ieee.org/ieee/802.1Qbu/5464/) |
| --- | --- | --- |
| Layer | Ethernet MAC (802.3) | Bridge (802.1Q), rolled into 802.1Q-2018 |
| Adds | **MAC Merge sublayer** joining an **express MAC (eMAC)** and a **preemptable MAC (pMAC)** to one PHY | A **frame preemption status** (express or preemptable) per traffic class |
| Effect | Express frames can interrupt a preemptable frame, which resumes afterwards | Says which traffic goes to which MAC and how preemption works with CBS and Qbv |

The PHY does not know about preemption.

## Fragments

- A preemptable frame can be interrupted only after **60 octets** have been sent and if at least **64 octets** remain, CRC included. The final fragment is at least 64 octets; a receiver may ask for larger non-final fragments (+0, 64, 128 or 192 octets).
- Each non-final fragment ends with an **mCRC** covering the frame so far; the final fragment carries the original FCS.
- Frame counts and fragment numbering detect a lost fragment, so an invalid frame is never reassembled.
- Preemption is enabled on a link only after **verification** that the other end supports it (negotiated with LLDP and checked with verify frames).
- So an express frame waits at most for the largest non-interruptible piece: **124 octets** in the common configuration (LS19 §IV-C).

## Hold and release

The MAC Merge Service Interface (MM_CTL.request with hold_req = HOLD or RELEASE) lets the bridge **stop preemptable frames from starting**, not just interrupt them. Qbv uses it through two gate operations scheduled like any gate event:

- **Set-And-Hold-MAC**: preemptable frames stop being sent;
- **Set-And-Release-MAC**: they may be sent again.

Scheduling Set-And-Hold-MAC 124 octet-times before the window of a time-critical class ensures that **no fragment at all** is on the wire when the window opens.

Without preemption, an express frame that arrives while a pMAC frame is being sent waits for the whole frame; if both are ready at once, the express frame goes first.

## Per-class status (802.1Qbu)

- One **frame preemption status table** per port: each traffic class is express or preemptable; all priorities mapped to a class share its status. The default is express for all.
- A preemptable frame is **not eligible** for transmission while a hold request is active or while an earlier preemptable frame is still unfinished.
- Any transmission selection algorithm (for example [CBS](./ieee-802-1qav.mdx)) may be used with preemption.

## When preemption is enough

- The gain shrinks as **link speed grows**: without preemption the worst blocking is one maximum frame, which is long at 100 Mbit/s and short at 10 Gbit/s.
- For CPRI fronthaul at high speed, simulations found that preemption reduces jitter but **not enough**; a Qbv configuration met the jitter target at the cost of more delay.
- A formal analysis (CPA) showed that standard Ethernet plus preemption can approach the worst-case latency of Qbv for control traffic in some automotive scenarios, but the result depends on the flows and their class mapping.
- **Preemption alone works only while express traffic is light.** Express frames still delay each other; above some volume, scheduling (Qbv) is needed.
- 802.3br sets **no limit** on how long a preemptable frame can be held. Express windows must stay short and the gaps between them must fit a full frame, so that preemptable frames still respect the maximum bridge transit delay (one second in 802.1Q).
