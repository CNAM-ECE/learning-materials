Bounded [latency](https://en.wikipedia.org/wiki/Latency_(engineering)) is useless if a cable cut loses frames for the hundreds of milliseconds it takes to reroute. Frame Replication and Elimination for Reliability ([FRER](https://1.ieee802.org/tsn/802-1cb/)) sends every frame along several paths in parallel, so a single failure costs no frame and no switchover time.

## 1. Definition

**Frame Replication and Elimination for Reliability**, [IEEE 802.1CB](https://1.ieee802.org/tsn/802-1cb/), is per-frame 1+1 (or 1+n) redundancy. The frames of a stream are numbered and sent on two or more maximally disjoint paths. They are then merged, and the extra copies are deleted. Nothing detects the failure and nothing [switches](https://en.wikipedia.org/wiki/Network_switch) over, so a path failure causes no interruption [3].

Replication and elimination can happen in the end stations themselves or in [bridges](https://en.wikipedia.org/wiki/Network_bridge). A non-redundant talker can then use a redundant network.

## 2. The functions on each side

<FrerFunctionsFigure caption="Figure 3. The FRER functions. The replicating side identifies the stream, numbers it, splits it and adds a tag. The eliminating side reads the number, removes duplicates and watches for a silent path." />

| Function | Side | What it does |
| --- | --- | --- |
| Stream identification | Both | Recognises the stream from frame fields, as in [PSFP](/blog/per-stream-filtering-and-policing) |
| Sequence generation | Replicating | Gives each frame the next sequence number |
| Stream splitting | Replicating | Makes one copy per *member stream*, one member per path |
| Sequence encode / decode | Both | Carries the number in a tag: the 802.1CB redundancy tag (R-TAG), or the tags of the [HSR](https://webstore.iec.ch/en/publication/64423) and [PRP](https://webstore.iec.ch/en/publication/64423) industrial protocols (IEC 62439-3) |
| Individual recovery | Eliminating, optional | Removes duplicates within one member stream |
| Sequence recovery | Eliminating | Removes duplicates across members. The **vector** algorithm keeps a window of recently seen numbers and accepts frames out of order; the **match** algorithm only compares with the last number. |
| Latent error detection | Eliminating | Raises an alarm when a path delivers nothing, so that a hidden failure is repaired before a second one causes loss |

## 3. Where the paths come from

FRER assumes disjoint paths but does not compute them. In a bridged network, the paths come either from **path control**, [802.1Qca](https://standards.ieee.org/ieee/802.1Qca/5557/), where [IS-IS](https://www.rfc-editor.org/rfc/rfc1195) computes defaults and a controller adds explicit trees, or from a [CNC](https://1.ieee802.org/tsn/802-1qcc/) that computes paths and configures them directly [3]. The [SDN post](/blog/sdn-and-tsn-configuration) covers the controller side. At Layer 3, [IETF](https://www.ietf.org/) [DetNet](https://www.rfc-editor.org/rfc/rfc8655) provides the same service as *packet replication, elimination and ordering* (see [the DetNet post](/blog/ietf-detnet)).

## 4. What FRER does to the traffic

FRER removes loss, but it changes the traffic that the latency analysis sees. The 2026 tutorial on decentralised latency models lists three effects [4]:

1. **Longer frames.** The tag adds bytes to every frame, which increases the stream's frame size and burst.
2. **A bigger burst after merging.** Even after elimination, the merged stream must often be given twice the original burst to cover the worst case.
3. **Reordering after a repair.** Suppose the two paths have different delays and the faster path fails. When it comes back, the merge point receives old frames from the slower path and recent frames from the faster one. Both are valid and neither is eliminated, so the output is temporarily burstier, until the old frames are used up. Annex C.9 of 802.1CB discusses this case.

The tutorial suggests placing [Asynchronous Traffic Shaping](/blog/asynchronous-traffic-shaping) at the merge point to restore the original burst at once. The combination of FRER and [ATS](https://1.ieee802.org/tsn/802-1qcr/) is still being standardised [4].

In [network calculus](https://en.wikipedia.org/wiki/Network_calculus) terms, the arrival curve after elimination is not the talker's curve. It must allow for the extra burst of points 2 and 3. Any bound computed downstream of an elimination point is wrong if it uses the original curve.

## 5. Summary

| Property | Frame Replication and Elimination |
| --- | --- |
| Standard | IEEE 802.1CB |
| Acts on | Individual streams, around the relay of replicating and eliminating systems |
| Redundancy | 1+1 or 1+n, per frame, no switchover |
| Needs time synchronisation | No |
| Needs | Maximally disjoint paths, from 802.1Qca or a CNC |
| Analysis caveat | Larger frames and, after merging, a larger burst |
