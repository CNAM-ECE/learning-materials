[TSN](https://1.ieee802.org/tsn/) makes a bridged network deterministic. The [IETF](https://www.ietf.org/) Deterministic Networking ([DetNet](https://www.rfc-editor.org/rfc/rfc8655)) working group does the same for routed networks, and defines how the two fit together. This post summarises the charter and the architecture document, RFC 8655.

## 1. Definition

**DetNet** is both a working group in the IETF Routing Area and the architecture it standardises. The group works on deterministic data paths that run over Layer 2 bridged and Layer 3 routed segments and that bound [latency](https://en.wikipedia.org/wiki/Latency_(engineering)), loss, [delay variation](https://en.wikipedia.org/wiki/Packet_delay_variation) and reordering, with high reliability. It addresses the Layer 3 aspects and collaborates with [IEEE 802.1](https://1.ieee802.org/) TSN, which is responsible for Layer 2, towards a common architecture [1].

Figure 1 shows how DetNet integrates with what already exists. It does not replace [IP](https://www.rfc-editor.org/rfc/rfc791) or [MPLS](https://www.rfc-editor.org/rfc/rfc3031) forwarding, and it does not replace TSN. It adds two sub-layers to the nodes on the path, and lets an end system that only speaks TSN take part through an edge node [2].

## 2. Scope of the working group

The charter draws the boundary carefully [1].

**In scope**

- [unicast](https://en.wikipedia.org/wiki/Unicast) and [multicast](https://en.wikipedia.org/wiki/Multicast) (point-to-multipoint) flows, over wired and wireless networks;
- networks under a single administrative control, or a closed group of administrative control, such as campus networks and private WANs;
- the overall architecture: data plane, OAM, time synchronisation, management, control and security;
- a data plane built on IP and MPLS, and on Layer 2 encapsulations that run over them, such as pseudowires and GRE;
- a flow information model and [YANG](https://www.rfc-editor.org/rfc/rfc7950) models, independent of the protocol that carries them;
- the ability to reserve resources in advance, then release and reuse them.

**Out of scope**

- solutions for large groups of domains such as the Internet;
- a new path set-up protocol: the work is independent of the protocol used;
- in general, modifications of transport protocols, OAM, Layer 3 forwarding and encapsulations, which belong to other working groups with which DetNet coordinates.

The last item explains the shape of the architecture: DetNet composes existing IETF and IEEE mechanisms and specifies what is missing between them.

## 3. Two sub-layers

<SourceFigure
  id="rfc8655-fig2"
  caption="Figure 2. Figure 2 of RFC 8655: the DetNet data-plane protocol stack, with the functions of the service and forwarding sub-layers on the sending and receiving side."
/>

The data plane is described as two sub-layers above the existing lower layers [2].

- The **service sub-layer** provides service protection. At the source side it sequences packets, replicates flows and may encode packets; at the destination side it eliminates duplicates, merges flows and decodes.
- The **forwarding sub-layer** provides resource allocation and explicit routes. The actual queuing and shaping are normally performed by the underlying sub-network.

These map directly onto the three techniques described in [the deterministic networking post](/blog/deterministic-networking). The model is conceptual: not every sub-layer is needed in every network, and the RFC states that the separation is not a formal requirement [2].

## 4. Node types

Reading Figure 1 from left to right gives the vocabulary [2]:

| Node | Sub-layers | Role |
| --- | --- | --- |
| End system | Depends on the system | Source or destination of a flow. It may be unaware of DetNet, as the TSN end system in Figure 1 is |
| Edge node | Service and forwarding | Start or end of the DetNet service; can run a *service proxy* on behalf of an end system that is not DetNet-aware. Comparable to a provider edge [router](https://en.wikipedia.org/wiki/Router_(computing)) |
| Relay node | Service and forwarding | Interconnects forwarding paths to provide service protection, for instance replication and elimination |
| Transit node | Forwarding only | Carries the flow along its explicit route with its allocated resources, for instance an MPLS label switching router |

Two horizontal relations appear in the figure: the *end-to-end service* between applications, and the *DetNet flow* between the service sub-layers that implement it. Between nodes there is either a plain link or a **sub-network**, which may be a TSN bridged network, an [MPLS-TE](https://www.rfc-editor.org/rfc/rfc2702) network or an optical transport network [2].

## 5. Three planes

<SourceFigure
  id="rfc8655-fig7"
  caption="Figure 3. The DetNet planes, Figure 7 of RFC 8655: the northbound interface between end systems and controller plane functions (CPF), and the southbound interface between the CPF and DetNet nodes."
/>

RFC 8655 separates three planes [2]:

- the **application plane**, where a user agent and a flow management entity express what flows are needed, as traffic specifications;
- the **controller plane**, the aggregation of the control and management planes. Its Controller Plane Functions compute deterministic paths and install per-flow, per-hop behaviour. A Path Computation Element is the standard example [1][2];
- the **network plane**, made of the network interfaces of end systems and of the DetNet nodes.

This is the same separation that makes centralised [admission control](https://en.wikipedia.org/wiki/Admission_control) possible. A controller that receives a flow request through the northbound interface must decide whether the flow can be admitted without breaking existing guarantees before it writes anything through the southbound interface. That decision is the problem studied in [the reconfiguration post](/blog/dynamic-reconfiguration-of-tsn).

## 6. Crossing a TSN sub-network

<SourceFigure
  id="rfc8655-fig10"
  caption="Figure 4. Figure 10 of RFC 8655: DetNet IP nodes interconnected by an Ethernet domain, with the IP and Ethernet flow identifiers used at each stage."
/>

When DetNet nodes are interconnected by a TSN network, the DetNet flow has to be mapped to a TSN Stream [2]. In Figure 4 the first IP node adds a Layer 2 flow identifier, and the [bridges](https://en.wikipedia.org/wiki/Network_bridge) forward on that identifier alone. Each domain uses an identifier that is unique within that domain, either derived from the application flow or assigned by the domain.

Within the bridged segment, the DetNet architecture relies on the IEEE 802.1 mechanisms rather than defining its own [2]: the credit-based shaper ([802.1Qav](https://standards.ieee.org/ieee/802.1Qav/4401/)), time-gated queues ([802.1Qbv](https://standards.ieee.org/ieee/802.1Qbv/6068/)), cyclic queuing and forwarding ([802.1Qch](https://1.ieee802.org/tsn/802-1qch/)) and frame preemption ([802.1Qbu](https://standards.ieee.org/ieee/802.1Qbu/5464/) with [802.3br](https://www.ieee802.org/3/br/)). Bridges match a flow by destination [MAC address](https://en.wikipedia.org/wiki/MAC_address), [VLAN](https://en.wikipedia.org/wiki/VLAN) identifier and priority to find its Stream and [quality-of-service](https://en.wikipedia.org/wiki/Quality_of_service) requirements [3].

The vocabulary changes at the boundary, although the concepts do not [2]:

| TSN term | DetNet term |
| --- | --- |
| Talker | Source |
| Listener | Destination |
| Stream | Flow |
| Relay system (bridge) | Intermediate node |

## 7. Current work

Beyond the base architecture, the charter lists a controller plane framework, YANG models for device and link capabilities, and DetNet over wireless segments, naming IEEE 802.15.4 TSCH, 3GPP [5G](https://en.wikipedia.org/wiki/5G) URLLC, IEEE 802.11ax/be and LDACS as target radio technologies [1]. Two of these items are recorded as done on the working group page: the controller plane framework (RFC 9938) and the architecture for reliable and available wireless (RFC 9912). The remaining milestones concern an enhanced data plane and the requirements for scaling deterministic networks [1].

Use cases are collected in RFC 8578 and the problem statement in RFC 8557 [3].

:::note[Relation to this series]
DetNet says *that* resources must be allocated so that latency is bounded; it does not prescribe how to compute the bound. [Network calculus](https://en.wikipedia.org/wiki/Network_calculus) is one way to compute it, hop by hop or end to end, for whatever queuing mechanism the sub-network uses.
:::

### History

| Year | Event |
| --- | --- |
| 2007 | IEEE 802.1 creates the **AVB** task group: time-synchronised, low-latency streaming over Layer 2 |
| 2012 | AVB is renamed the **TSN** task group to serve industrial control |
| 2015 | The IETF creates the **DetNet** working group, to extend bounded latency, low jitter and high reliability to Layer 3 |
| 2019 | RFC 8557 (problem statement), RFC 8578 (use cases) and RFC 8655 (architecture) are published |

### RFC 8655: what DetNet provides

DetNet gives a flow a **bounded latency** (with a minimum and a maximum), **low loss** and **in-order delivery**, using three techniques:

| Technique | How |
| --- | --- |
| **Resource allocation** | Reserve buffers and bandwidth along the path, so that there is no congestion loss and the delay is bounded |
| **Service protection** | Packet replication, elimination and ordering (PREOF), the Layer 3 counterpart of [802.1CB](/blog/frame-replication-and-elimination), and network coding |
| **Explicit routes** | Fixed paths that do not change with routing convergence (MPLS TE, segment routing, SDN, IS-IS) |

Points marked in the reading of §2.1:

- DetNet flows **converge** with non-DetNet traffic on one infrastructure. DetNet does not exclude other flows, but they must not take the resources reserved for DetNet.
- There is **no restriction on topology**. A flow is characterised by a **maximum bandwidth**, and resources can be reserved by network management, by a central controller, or **on demand** through a distributed control plane such as RSVP.
- Some DetNet nodes need **synchronised clocks**, to sub-microsecond accuracy for some queue-control techniques.
- DetNet runs over **sub-networks** that are not DetNet-aware. The margin note on the PDF reads: *DetNet interconnects with non-DetNet topologies (sub-network technologies)*. TSN, MPLS TE and OTN are examples.
- A **compound flow** is split into **member flows** for service protection and merged back into one flow without duplicates by the service sub-layer. A **service sub-layer proxy** maps between DetNet and non-DetNet systems, adding or removing sequence information.

### RFC 8655 in detail

**Scope.** One administrative domain: a campus, a private WAN. Not the Internet. Resources are dedicated to DetNet flows; whatever a flow does not use is available to non-DetNet traffic only.

#### Vocabulary

| Term | Meaning |
| --- | --- |
| **App-flow** | The payload carried over DetNet, with no DetNet attributes |
| **DetNet flow** | Packets with a unique flow ID and DetNet headers |
| **Allocation** | Resources dedicated to a flow (reusable when idle) |
| **Reservation** | Resources from source to destinations |
| **Domain** | The DetNet-aware part of the network |
| **Edge node** | Source or destination of the service sub-layer (like an LER or PE) |
| **Relay node** | Service sub-layer (protection) between forwarding paths |
| **Transit node** | Forwarding sub-layer only (like an MPLS LSR) |
| **Link** | A physical link or a sub-network |
| **UNI** | User–network interface: encapsulation, status, synchronisation |
| **PRF / PEF / POF** | Packet replication, elimination and ordering functions; together **PREOF** |

| IEEE (TSN) | IETF (DetNet) |
| --- | --- |
| Talker | Source |
| Listener | Destination |
| Stream | Flow |
| Relay system (bridge) | Intermediate node |
| End station | End system (host) |

#### The service

DetNet QoS is stated as: **minimum and maximum latency**, bounded jitter, a **loss ratio**, and a **maximum misordering**. Only the **worst case** counts: priority queuing gives a better average but a worse worst case. The goal is to emulate legacy analogue or serial links, where latency is acceptable but **jitter is not** (it harms control stability). Jitter is reduced by the same mechanisms as resource allocation, plus sub-µs synchronisation and time-of-execution fields.

#### Three techniques, eight combinations

| Combination | Example |
| --- | --- |
| Resource allocation alone | AVB (MSRP plus shapers) |
| Explicit routes + service protection | Seamless redundancy on a ring (HSR, PRP) |
| All three | Maximum protection |
| Priority + over-provisioning only | Works only with little non-critical traffic and no failures |

- **Resource allocation.** Buffers and bandwidth per flow: no contention loss and bounded latency, provided the source is **rate limited**. Hence no congestion control is needed, and App-flows ignore ECN. Every hop regulates the rate; ingress policing and shaping protect non-DetNet traffic. Without enough provisioned resources, the reservation is **rejected**.
- **Service protection.** Encoding against media errors; PRE against equipment failure, over disjoint paths (1+1 or 1+n hitless). **PRE is not failover**: each packet is selected, and no failure detection is needed. Relays that replicate and eliminate mid-path tolerate several failures. The merge point **buffers** to equalise path delays. PREOF hides congestion signals, so member flows are treated as non-congestion-controlled.
- **Explicit routes.** Dynamic routing (IS-IS, OSPF) causes loss and misordering during topology changes; explicit routes keep the path fixed. They are set up with RSVP-TE, segment routing, SDN or IS-IS. Rings need little wiring but add hops and latency.

#### Flows and end systems

| End system | Knows about | Flow format |
| --- | --- | --- |
| DetNet-unaware | Nothing; needs a **proxy** | App-flow |
| f-aware | Forwarding sub-layer (resources) | f-flow |
| s-aware | Service sub-layer (sequencing) | s-flow |
| sf-aware | Both | sf-flow |

- **Synchronous** flows rely on sub-µs synchronisation and time-shared resources; **asynchronous** flows are analysed with worst-case interference and specified by maximum packet size, interval and maximum transmissions per interval. The trade-off is scheduling effort against buffer space.
- An App-flow can be CBR or VBR, at Layer 1 to 3; VBR is reserved at its peak.
- The fundamental shift: resources are **reserved before the application starts**.
- Hops that are not DetNet-aware must be configured, and add buffering, latency and jitter downstream.

#### Planes

DetNet is a branch of traffic engineering (TEAS), with three planes:

| Plane | Contents | Interface |
| --- | --- | --- |
| **Application** | User agents request service through a flow management entity, with a **TSpec** | Northbound |
| **Controller** | Control and management (plus measurement): a controller plane function (CPF: PCE or NME) computes deterministic paths with redundancy and PRE, and installs per-flow, per-hop behaviour | Southbound |
| **Network** | Data plane and OAM: NICs, routers, MPLS switches | — |

Nodes report their capabilities and topology up; the CPF pushes the flow characterisation down. Reservation alone is not enough: standard data-plane algorithms (CBS, TAS, CQF, preemption) are needed to compute per-hop latency and buffers from the flow specification. All of them except preemption also apply to routers and non-Ethernet media.

#### Flow identification across domains

The flow ID must be visible to the layer that forwards. When the forwarding paradigm changes (IP, MPLS, Ethernet), the flow ID, and the sequence number with it, is **exported** to the lower layer instead of relying on deep packet inspection. A relay maps IDs: a TSN stream ID in a bridged network, its own label in MPLS. An aggregate flow is not a compound flow. Flow aggregation (MPLS hierarchy, DSCP) is how DetNet scales.

#### Security and privacy

- Security protects the **QoS**: secure control, confidentiality, availability. DetNet inherits IP and MPLS security.
- Authenticate and authorise, especially controllers: ACTN for centralised control, protocol security for distributed control.
- Confidentiality with IPsec (IP) or MACsec (Layer 2).
- Availability: admission control against denial of service; authentication against man-in-the-middle **delay attacks**. Time synchronisation security is critical (RFC 7384).
- Privacy: QoS markings and per-node flow IDs let an attacker correlate traffic.

### DetNet compared with TSN

Yang et al. [5] §8, completed with Lo Bello and Steiner [4] §IV-G:

| Aspect | TSN (IEEE 802.1) | DetNet (IETF) |
| --- | --- | --- |
| Layer | Layer 2 bridged LANs (some exceptions, such as 802.1AS-Rev and 802.1CB, also apply above) | Layer 3 (IP and MPLS), over Layer 2 sub-networks |
| Latency | Upper bound | Upper **and lower** bound, to limit jitter |
| Data plane | Ethernet | IP, MPLS; runs over TSN, MPLS TE or OTN; multi-layer systems possible |
| Reliability | 802.1CB | PREOF, the same idea |
| Time synchronisation | 802.1AS | Reuses IEEE 1588 and 802.1AS |
| Security | Little in the TSN standards; left to 802.1 security | A dedicated security document: delay attacks, path manipulation, authentication of nodes |
| Maturity in 2019 | Many published standards in use | Mostly drafts; now several RFCs (IP, MPLS, over TSN, YANG, security) |

**Coexistence with best effort.** DetNet gives critical flows a higher priority than best effort; since both are limited by reservations, the network stays stable ([5] §5.1).

**Industry view ([4]).** Large networks could benefit from TSN and DetNet together, to keep guarantees across routers. But industrial automation (OPC UA) and automotive (SOME/IP in Adaptive AUTOSAR) already have their own Layer 3 and higher solutions, so it was unclear in 2019 how far DetNet would be adopted there.

**Future work named in 2019.** For TSN: interconnection with external networks, simpler management, security and privacy. For DetNet: reliable resource sharing over Layer 2, and integration with existing networks.
