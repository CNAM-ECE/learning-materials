Gates, cyclic queues and time-gated [policing](https://en.wikipedia.org/wiki/Traffic_policing_(communications)) all assume that every [bridge](https://en.wikipedia.org/wiki/Network_bridge) reads the same time. [IEEE 802.1AS](https://1.ieee802.org/tsn/802-1as-2020/) is the standard that provides that time. This post explains how it works and what an analysis has to assume about it.

## 1. Definition

**[IEEE 802.1AS](https://1.ieee802.org/tsn/802-1as-2020/)**, *Timing and Synchronization for Time-Sensitive Applications*, defines the **generalised [Precision Time Protocol](https://standards.ieee.org/ieee/1588/6825/) (gPTP)**. gPTP is a tightly constrained profile of [IEEE 1588](https://standards.ieee.org/ieee/1588/6825/) PTP. It distributes time from one reference clock, the *grandmaster*, through bridges and end stations, with sub-microsecond precision [1][2].

Two properties set it apart from using PTP over an ordinary LAN:

- **Every device takes part.** Each bridge on the path is a *time-aware system* that measures its links and its own residence time. It is not a transparent box that adds unknown delay [2].
- **Time travels with the network.** No separate timing network is needed. The messages are ordinary [Ethernet](https://standards.ieee.org/ieee/802.3/10422/) frames between neighbours.

The table in [the TSN toolbox post](/blog/tsn-toolbox) shows which [TSN](https://1.ieee802.org/tsn/) tools depend on gPTP. Scheduled traffic ([802.1Qbv](https://standards.ieee.org/ieee/802.1Qbv/6068/)), cyclic queuing ([802.1Qch](https://1.ieee802.org/tsn/802-1qch/)) and time-based stream gates ([802.1Qci](https://1.ieee802.org/tsn/802-1qci/)) need it. The credit-based shaper and asynchronous [traffic shaping](https://en.wikipedia.org/wiki/Traffic_shaping) do not.

## 2. Who is the master

<CommonsFigure
  id="gptp-hierarchy"
  caption="Figure 2. A gPTP domain. The grandmaster's time flows down a tree. On every link one end is a clock master port and the other a clock slave port. Bridges forward time and add the corrections for cable and residence delay."
/>

The **best master clock algorithm ([BMCA](https://standards.ieee.org/ieee/1588/6825/))** compares the clocks it hears about and elects a grandmaster. Each port then becomes a master port (sending time downstream) or a slave port (receiving time from upstream). Ports on redundant links become passive. The result is a spanning tree of time, as in Figure 2 [2].

The figure uses the master/slave port names of the original standards. Recent revisions of IEEE 1588 also allow the names timeTransmitter and timeReceiver.

## 3. Measuring a link

### The PTP exchange

<CommonsFigure
  id="ptp-timing"
  caption="Figure 3. The basic PTP exchange between a time server (master) and a network element (slave). The four timestamps let the slave separate the path delay from its own clock offset."
/>

Write $d$ for the one-way delay, assumed equal in both directions, and $o$ for the offset of the slave clock from the master clock. With the timestamps of Figure 3, the master sends at $T_1$ and the slave receives at $T_1'$; the slave sends at $T_2$ and the master receives at $T_2'$. Then

$$
T_1' = T_1 + d + o, \qquad T_2' = T_2 + d - o,
$$

which give

$$
o = \frac{(T_1' - T_1) - (T_2' - T_2)}{2}, \qquad d = \frac{(T_1' - T_1) + (T_2' - T_2)}{2}.
$$

The symmetry assumption is the weak point: any asymmetry between the two directions goes straight into the offset as an error of half the asymmetry.

### Peer delay in 802.1AS

<PeerDelayFigure caption="Figure 4. Peer delay measurement in 802.1AS. Each pair of neighbouring ports measures its own link. The follow-up message carries the precise send time t3 (two-step operation)." />

gPTP does not measure the delay from master to slave end to end. Each pair of neighbours measures only the link between them, using the **peer-to-peer delay mechanism** of Figure 4. The time itself then travels in `Sync` and `Follow_Up` messages. At each hop the bridge adds to a correction field:

- the measured delay of the link the message arrived on;
- its own **residence time**, from reception to forwarding;
- a correction for the **rate ratio**, the frequency difference between neighbouring clocks.

Errors therefore accumulate hop by hop. Queuing does not add error, because each bridge measures how long the message stayed inside it and adds exactly that time to the correction field.

## 4. What changed in the 2020 revision

The 2020 revision of 802.1AS improved the accuracy of time measurement and added **multiple time domains**, so that a device can follow several grandmasters for redundancy [2]. The task group's work on the revision also covered [link aggregation](https://en.wikipedia.org/wiki/Link_aggregation), faster changeover between grandmasters, and redundant paths [3].

## 5. What an analysis must assume about time

A schedule computed for perfectly synchronised clocks fails on real hardware. The literature on scheduled traffic therefore models a **maximum synchronisation error**: the largest offset between two non-faulty clocks. Windows are widened by that margin [4]. The 802.1AS revision allows a finer model, with an error per node that depends on its role and its hop distance from the grandmaster [4].

Two practical lessons come from a testbed study of 17 scheduling methods [4]:

1. **Synchronisation messages are traffic too.** If time-triggered frames collide with PTP messages, synchronisation can fail within its period. The runtime error then exceeds the bound the schedule assumed, causing missed deadlines or network failure. The schedule must leave room for gPTP.
2. **The error bound is an input to the guarantee.** A worst-case delay computed for scheduled traffic is only as valid as the synchronisation error it assumed.

A review of [industrial IoT](https://en.wikipedia.org/wiki/Industrial_internet_of_things) technologies makes the same point from the other side. With even small time errors, carefully aligned windows can drift apart. Scheduled traffic is then delayed by a whole cycle, and the problem grows with the size of the network [5].

## 6. Summary

| Element | Role |
| --- | --- |
| Grandmaster | Reference clock of a gPTP domain, elected by the BMCA |
| Master and slave ports | Direction of time on each link |
| `Pdelay_Req`, `Pdelay_Resp`, `Pdelay_Resp_Follow_Up` | Measure the delay of one link between neighbours |
| `Sync`, `Follow_Up` | Carry time down the tree, with accumulated corrections |
| Rate ratio | Frequency difference between neighbouring clocks |
| Synchronisation error | The bound that schedules and analyses must assume |
